Case Study

Curio

Personalized News Digest Platform

01 — Problem

Most news aggregators show the same feed to everyone. I wanted to build a system where each user gets a personalized digest of only the categories they care about, delivered at a frequency they control — without the backend making redundant API calls for every single user.

02 — Architecture
flowchart TD
    A[Node-cron 6AM] -->|addToQueue| B[BullMQ newsFetch]
    B --> C[Worker]
    C -->|fetch 13 categories| D[NewsData.io API]
    D -->|upsert articles| E[(MongoDB)]
    C -->|invalidate| F[(Redis Cache)]

    G[User visits /news] --> H{Redis cache?}
    H -->|hit| I[Serve instantly]
    H -->|miss| J[Query MongoDB]
    J -->|cache 30min| F
    J --> I

    K[Node-cron 8AM] -->|addToQueue| L[BullMQ digest]
    L --> M[Worker]
    M -->|$expr filter| E
    M -->|aggregation| E
    M -->|p-limit 10| N[N8n Webhook]
    N --> O[Gmail SMTP]
    M -->|updateMany| E
03 — Key Technical Decisions
  • Category-level caching over user-level: Articles are identical for all users in a category. Caching per category means 1000 users following technology share one cache entry instead of 1000.
  • MongoDB $expr for digest scheduling: Instead of loading all users into memory and filtering in JavaScript, the query filters directly in MongoDB — only users whose digest is due today are returned.
  • Promise.allSettled + p-limit: Sending 100 emails concurrently would overwhelm N8n. p-limit controls throughput at 10 concurrent sends. allSettled means one failure doesn't stop the rest.
  • Only update successful sends: lastNotifiedAt is only updated for users whose email actually sent — tracked via Promise.allSettled result status mapping back to user IDs.
  • TTL index for auto cleanup: Articles auto-delete after 7 days via MongoDB TTL index — no manual cron needed for cleanup.
04 — Impact
  • 3 total DB calls to process the entire daily digest — regardless of user count
  • 130+ articles fetched and stored daily across 13 categories
  • Category cache shared across users eliminates N×13 redundant queries
  • Redis pipeline for bulk cache invalidation — single round trip

NanoURL

URL Shortener with Quota Management

01 — Problem

Build a URL shortening service that generates unique short codes, handles authentication securely, and enforces monthly usage limits per user — automatically resetting quotas without manual intervention.

02 — Architecture
flowchart TD
    A[User submits URL] --> B[Express API]
    B --> C{Authenticated?}
    C -->|No| D[Redirect to login]
    C -->|Yes| E{Quota remaining?}
    E -->|No| F[Return 429 limit reached]
    E -->|Yes| G[Generate short code]
    G --> H[(MongoDB — save mapping)]
    H --> I[Return short URL]

    J[Node-cron — 1st of month] --> K[Reset all user quotas]
    K --> H
03 — Key Technical Decisions
  • Hash-based short codes: Generated using a hashing function against the original URL + timestamp to ensure uniqueness without sequential IDs.
  • Node-cron for quota reset: Runs on the 1st of every month, updating all user documents in a single updateMany — no per-user cron jobs.
  • Passport.js for auth: Session-based authentication with email verification flow before users can create short links.
04 — Impact
  • Live and deployed on Render
  • Automated monthly quota reset — zero manual intervention
  • Full auth flow with email verification and password reset
